## Plan Phase

**Duration**: ~5 minutes (initial gray-areas discussion → plan commit at 21:31)
**Rounds**: 4 — research dispatch → gray-areas Q&A → architect/planner generation → reviewer feedback applied in-place

What was built and why:

llmscope is a local desktop LLM proxy gateway. Captures every LLM API call from any app on the user's machine — browser, IDEs, CLIs (Claude Code, Cursor, Codex) — by injecting an addon into an existing debugging proxy (whistle or mitmproxy). Surfaces requests in a localhost dashboard with token usage, source-app attribution, and replay. The genuine gap vs existing OSS: every other "LLM proxy" is either an explicit reverse-gateway clients opt into (LiteLLM, Portkey, Helicone) or a Claude-Code-only `ANTHROPIC_BASE_URL` redirector. None offer transparent multi-app capture across providers.

Key planning decisions:

| Decision | Choice | Why |
|---|---|---|
| Architecture | CLI installer that injects an addon into an existing host proxy | Sidesteps the CA-cert UX, which is the hardest part of any local interceptor |
| Priority | whistle first, mitmproxy second | User already runs whistle; whistle stays in TS/Bun toolchain |
| Storage | SQLite + FTS5 | Single file, fast aggregations, FTS for prompt search; JSONL export as a feature |
| UI stack | React + Vite + Tailwind v4 + shadcn-style primitives | Familiar; small bundle |
| Source attribution | UA + headers + request-shape fingerprints + manual user re-tagging | No port→PID mapping (cross-platform nightmare) |
| Replay scope | Read-only re-send for v1 | Editable replay deferred to v2 per PRD |

Plan reviewer found 2 critical + 4 high + 4 medium issues; all 10 + 4 coverage holes patched in-place before any code was written.

## Learnings

What worked well:

- **Plan-first with reviewer pass before any code.** The pre-implementation review caught 2 critical + 4 high issues that would have been much more expensive to fix mid-build.
- **Incremental ingest milestone at step 18.** Having an end-to-end "real whistle plugin → real daemon → real DB" working before any UI work meant the rest of the build was just adding views over a known-good pipeline.
- **Empirical debug approach.** When the whistle plugin didn't fire, dropping into whistle's `load-plugin.js` source rather than guessing at protocols was the only way to make progress. Documentation lied (or was incomplete); source code didn't.
- **Diagnostic logs unconditional, not env-gated.** When the plugin runs as a forked child process, env vars don't necessarily propagate. Logging to a file unconditionally meant we always had visibility regardless.
- **Code review as a final gate.** The reviewer caught two real correctness/security issues (SSRF, pipe race) that I'd glossed over.

What to improve:

- **Test coverage for streaming bodies in the whistle plugin was thin.** The `'data'` listener race wasn't caught by my single-shot e2e test because the body was tiny enough to fit in one chunk. A multi-megabyte body test would have caught it.
- **Whistle's protocol semantics are under-documented.** Took 4 iterations of plugin code to find the right hook. A first-class "what hook fires when?" matrix in whistle's docs would have saved hours.
- **Node fetch + HTTPS_PROXY behavior is a known foot-gun**, but I didn't catch it in the architecture phase — only when a real test failed silently. Architecture review should include "how do typical Node clients behave under proxying?"

Patterns to remember:

- For Node-based CLIs that use `fetch()`: `NODE_USE_ENV_PROXY=1` + `HTTPS_PROXY` + `NODE_EXTRA_CA_CERTS` is the minimum-viable proxy setup. Without `NODE_USE_ENV_PROXY=1`, the other two are useless.
- When tee'ing a stream for capture + pipe, never attach `'data'` directly to the source — always tee through `PassThrough`.
- For SSRF prevention on any user-influenced URL fed to `fetch()`, validate (a) protocol whitelist + (b) hostname allowlist. Don't rely on "but the URL is from our own DB."
- bun:sqlite's `db.query<R, P>()` uses the second generic for parameter tuple typing; mismatching it produces confusing "expected 0 args" errors.
- bun's lockfile format changed from binary `bun.lockb` to text `bun.lock` (`lockfileVersion: 1`) in 1.3 and is not backward-compatible with 1.1.x — pin CI to match local.
