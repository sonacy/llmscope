# PRD: llmscope

> Generated by `/plan` on 2026-04-24

## Overview

`llmscope` is a local desktop tool that captures and analyzes LLM API traffic from any app on the user's machine — browser, native desktop apps, CLIs (Claude Code, Cursor, Codex), IDE plugins. Rather than building its own TLS-intercepting proxy, llmscope ships as a CLI installer that detects existing locally-installed debugging proxies (whistle, mitmproxy) and injects an LLM-aware addon into them. The addon auto-detects requests with LLM shape (`model` + `messages` + optional `tools`), reassembles streamed responses (HTTP, SSE, WebSocket), and ships events to a local daemon that writes them to SQLite. A localhost dashboard (React + shadcn) renders request/response details, token-usage charts, source-app attribution (which client made the call), and a replay tool.

The product targets a clear gap: every existing OSS LLM proxy is either an explicit reverse-gateway clients opt into (LiteLLM, Portkey, Helicone) or a single-vendor `ANTHROPIC_BASE_URL` redirector. None offer transparent multi-app capture across providers with source attribution. By riding on host proxies the user already trusts, llmscope sidesteps the CA-cert install UX problem and inherits mature TLS interception for free.

## User Stories

- As a **dev who already runs whistle locally**, I want to install an llmscope addon with one command and immediately see every LLM call from my browser, IDE, and CLIs in one dashboard.
- As a **dev debugging Claude Code or Cursor**, I want to see the full system prompt, tool definitions, and streamed response so I can understand what the agent is actually sending — not what its docs claim.
- As a **dev measuring spend**, I want a chart of tokens-per-day broken down by source app and provider so I know which tools are burning my quota.
- As a **dev tuning a prompt**, I want to replay a captured request — first read-only to verify reproducibility, later with edits — so I can iterate without rewiring the source app.
- As a **dev with multiple devices/tools**, I want llmscope to identify the source of each request (browser vs Claude Code vs Cursor vs Codex) automatically using UA + request-shape heuristics, so I don't have to guess.
- As a **dev who already runs mitmproxy**, I want the same llmscope experience with a `mitmdump -s` one-liner — no migration, no second proxy.

## Acceptance Criteria

### Detection & Capture

- [ ] CLI command `llmscope init` detects whether `whistle` and/or `mitmproxy` are installed on the user's PATH and reports which addons can be activated.
- [ ] CLI command `llmscope install <whistle|mitmproxy>` installs the corresponding addon into the host proxy's plugin/script directory and prints the one-liner to start capture.
- [ ] Addon classifies an HTTP request as "LLM" if it has a JSON body containing both `model` (string) and either `messages` (array) or `prompt` (string), OR matches a known endpoint of OpenAI/Anthropic/Google/Bedrock/Cohere/Mistral/Together/Groq/OpenRouter.
- [ ] Addon captures full request body, response body, request headers, response headers, status code, start/end timestamps, transport type (`http`/`sse`/`ws`).
- [ ] SSE responses are reassembled — the addon emits a single event with the merged response, not one event per chunk.
- [ ] WebSocket sessions (OpenAI Realtime API) are captured as a single event with the message timeline preserved.
- [ ] Capture works for chunked transfer encoding, gzip/br/zstd compressed responses, and HTTP/2.
- [ ] Capture for non-LLM traffic is dropped before reaching the daemon (no privacy leak of unrelated requests).

### Source Attribution

- [ ] Each captured event has a `source` field with at least `{ kind, label, confidence }`.
- [ ] Built-in fingerprints recognize: Claude Code (UA `claude-cli/...`, `anthropic-beta` headers), Cursor (UA contains `Cursor/`, hits `api2.cursor.sh`), Codex CLI (UA `OpenAI/Codex-CLI`), generic browsers (Chrome/Firefox/Safari UAs hitting `chat.openai.com`, `claude.ai`, `gemini.google.com`).
- [ ] Request-shape fingerprints flag: `system.role == 'system' && tools[].name in known-claude-code-tools` ⇒ Claude Code; specific Cursor system-prompt prefixes ⇒ Cursor.
- [ ] Users can manually re-tag a request's source via the UI; that mapping is remembered for future requests with the same UA.
- [ ] Source attribution falls back to `{ kind: 'unknown', label: <UA string> }` rather than failing.

### Storage & Daemon

- [ ] Daemon listens on `127.0.0.1:<port>` (localhost-only by default; configurable port).
- [ ] Daemon writes events to `~/.llmscope/db.sqlite` with FTS5 indexing on prompt/response text.
- [ ] Schema migrations run on daemon startup; old DBs are upgraded in place.
- [ ] Daemon serves the UI at `http://localhost:<port>/` and a JSON API at `/api/*`.
- [ ] `llmscope export --format jsonl --since <date>` exports raw events to JSONL for sharing/forensics.
- [ ] DB grows beyond a configurable size cap (default 1 GB) → daemon evicts oldest events with a warning logged.

### Dashboard UI

- [ ] List view: paginated table of recent events with columns `time | source | provider | model | tokens (in/out) | latency | status`.
- [ ] Filters: source app, provider, model, status (ok/error), time range, full-text search.
- [ ] Detail view: full request/response JSON, headers, streaming timeline (for SSE/WS), parsed token usage and cost (using a local pricing table).
- [ ] Charts: tokens/day stacked by provider, requests/day stacked by source app, top models by spend.
- [ ] Replay v1 (read-only): one-click "re-send this exact request, store the new response as a sibling event for diff comparison."
- [ ] Replay v2 (editable, post-v1): user can edit `model`, `temperature`, `messages`, `tools` and submit; result stored alongside.
- [ ] UI works in Chrome/Safari/Firefox latest, no IE/legacy.

### CLI

- [ ] `llmscope init` — interactive setup, detects host proxies, asks user which to wire up.
- [ ] `llmscope install <target>` — installs addon non-interactively (for scripts).
- [ ] `llmscope start` — starts the daemon (idempotent).
- [ ] `llmscope stop` — stops the daemon.
- [ ] `llmscope open` — opens dashboard in default browser.
- [ ] `llmscope status` — shows daemon PID, port, DB size, events captured today.
- [ ] `llmscope export ...` — JSONL export.
- [ ] `llmscope --version` and `llmscope --help`.

## Technical Requirements

- **Language/runtime**: TypeScript on Bun for CLI/daemon/UI/whistle-addon (single toolchain). Python 3.11+ for the mitmproxy addon (separate dir, `pyproject.toml`).
- **Storage**: SQLite via `bun:sqlite` (built-in, zero deps).
- **UI**: React 18+, Vite, Tailwind, shadcn/ui, TanStack Table for the list view, recharts or visx for charts.
- **Schema**: shared TS types in `packages/core` define the event contract; both the whistle addon (TS) and Python addon emit conforming JSON over HTTP.
- **Streaming reassembly**:
  - SSE: parse `data: <json>` frames, accumulate `delta` fields per provider's known shape.
  - WebSocket: store full message log, reconstruct conversation per provider's protocol.
  - Compression: addons must decompress (gzip/br/zstd) before forwarding to daemon.
- **Provider detection**: provider-agnostic shape matching first (`{ model, messages|prompt }`), then enrichment from a registry of known endpoints/UAs.
- **Privacy**: no telemetry, no outbound network calls from llmscope itself. All data stays on `127.0.0.1`.
- **Security**: daemon binds to `127.0.0.1` only, not `0.0.0.0`. API uses a per-session bearer token written to `~/.llmscope/token` (mode 0600).
- **Cross-platform**: macOS, Linux primary. Windows best-effort (paths use `node:path`).
- **Performance**: addon overhead < 5ms per intercepted non-LLM request (fast-path drop). Capture pipeline must handle 100 events/sec sustained.
- **Pricing table**: bundled JSON at `packages/core/src/pricing.json`, updated manually for v1; later: optional remote refresh.

## Out of Scope

- Building llmscope's own TLS-intercepting proxy. Defer to v2+ — would require shipping a CA cert and the full UX of `mkcert`-style trust install.
- Hosted/cloud mode. Local-only.
- Team sharing / multi-user / RBAC / SSO.
- Cost dashboards across multiple users or org-wide rollups.
- Real-time response modification (the addon is read-only; no man-in-the-middle prompt injection).
- Charles, Proxyman, Fiddler, HTTP Toolkit addon support — defer.
- Mobile (iOS Simulator / Android Emulator) traffic capture — works incidentally if user routes the simulator through whistle/mitmproxy, but no specific support.
- Auto-updates of the pricing table.
- IDE-native extensions (VS Code, JetBrains panel) — defer.
- Editable replay (v2 — listed as post-v1 acceptance criterion above, not v1 scope).

## Open Questions

- [ ] Distribution: publish CLI to npm as `llmscope`? Bun-only or also support `node` runtime so users without Bun can `npm i -g llmscope`? (Recommendation: Bun primary, `bunx llmscope` works without install; do not ship Node build for v1.)
- [ ] Whistle plugin packaging: whistle plugins are npm packages prefixed `whistle.`. Should the addon be `whistle.llmscope` (separate package) or carried inside the main repo? (Recommendation: separate `whistle.llmscope` package in the monorepo, published independently.)
- [ ] mitmproxy distribution: a single `addon.py` script copied to a known path? Or a `pip install llmscope-mitmproxy`? (Recommendation: ship a single self-contained `.py` that the CLI writes to `~/.llmscope/mitmproxy_addon.py`; users run `mitmdump -s`. No pip release for v1.)
- [ ] WebSocket capture in whistle: confirm whistle's plugin API exposes WS frames bidirectionally. If not, deprioritize WS for v1 whistle path; mitmproxy supports it.
- [ ] Pricing table source-of-truth: ship a hardcoded snapshot, or pull from a community-maintained list (e.g., LiteLLM's `model_prices_and_context_window.json`)? Recommendation: pull from LiteLLM's table at build time, snapshot.

## Notes

- User pivoted away from "build our own proxy" to "be a plugin for the proxy the user already runs." This is the right call for v1 — the CA-cert UX is the hardest part of any local interceptor and the host proxy already solved it.
- Whistle is prioritized over mitmproxy for v1 because (a) the user already uses whistle, (b) whistle stays in the TS/Bun toolchain, (c) whistle has strong CN adoption which matches the user's audience.
- mitmproxy second because it's the universal default for English-speaking devs and is scriptable enough that the addon is a single Python file.
- Keep the addon contract minimal — just POST JSON to `/api/ingest`. That makes adding Charles/Proxyman/HTTP Toolkit later a 1-2 day job each.
- Source attribution is the **defining** feature versus all existing tools. Get the fingerprint table right.
